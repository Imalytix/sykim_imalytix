이번엔 역대 최대 규모 변경입니다 — `images`/`request_logs` 2테이블 구조를 버리고 `users`/`verification_requests`/`request_images`/`ai_provider_calls`/`verification_evidence`/`verification_results` 6테이블 구조(schema.v2.md 제안)로 교체했습니다. **재실행 전까지는 분석 결과가 DB에 전혀 기록되지 않습니다** — 분석 자체(3-LLM 호출, 점수 산출, 화면 표시)는 정상 동작하고(직접 테스트해서 확인함), 기록만 조용히 실패합니다(`PGRST202` — 이제 익숙하실 에러입니다). 재실행하면 바로 해결됩니다.

**⚠️ 기존 `images`/`request_logs` 테이블은 지우지 않았습니다** — 그 안의 과거 분석 기록이 새 테이블로 자동 이전되지 않습니다. 필요 없으시면 "지워도 돼"라고 말씀해주시면 별도 DROP 문 드리겠습니다.

### 2) Supabase 대시보드 — Authentication 설정

SQL만으로는 로그인이 안 됩니다. 대시보드에서 직접 하셔야 하는 것들:

**a) Site URL / Redirect URLs 등록** (Authentication → URL Configuration)
- Site URL: `http://localhost:3000` (배포 후엔 실제 도메인으로 교체)
- Redirect URLs에 추가: `http://localhost:3000/auth/callback` (배포 후 프로덕션 URL도 같은 패턴으로 추가)

**b) Google 소셜 로그인 활성화** (Authentication → Sign In / Providers → Google)
1. [Google Cloud Console](https://console.cloud.google.com) → OAuth 클라이언트 ID 생성 (유형: 웹 애플리케이션)
2. 승인된 리디렉션 URI에 Supabase가 제공하는 콜백 URL 입력 (Supabase 대시보드의 Google 설정 화면에 정확한 URL이 표시됩니다 — 보통 `https://<project-ref>.supabase.co/auth/v1/callback`)
3. 발급받은 Client ID / Client Secret을 Supabase 대시보드의 Google provider 설정에 입력 후 활성화(Enable)

**c) 카카오 소셜 로그인 활성화** (Authentication → Sign In / Providers → Kakao)
1. [Kakao Developers](https://developers.kakao.com)에서 앱 생성
2. 카카오 로그인 활성화 + Redirect URI에 Supabase 콜백 URL 등록
3. REST API 키를 Supabase 대시보드의 Kakao provider 설정에 입력 후 활성화

**참고**: Google/카카오 둘 다 안 하셔도 이메일/비밀번호 로그인은 바로 됩니다(Supabase Auth 기본 기능이라 추가 설정 불필요) — 소셜 로그인만 이 단계가 필요합니다. 시간 없으시면 이메일 로그인만 먼저 켜두고 소셜은 나중에 추가하셔도 됩니다.

## 구현 내용

### 1) Supabase Auth 클라이언트 연동 — 왜/어떻게/언제

**왜 필요한가**: `SUPABASE_SERVICE_ROLE_KEY`로 만든 기존 클라이언트(`lib/supabase/client.ts`)는 RLS를 완전히 우회하는 서버 전용 키라, "지금 로그인한 사람이 누구인지" 자체를 모릅니다. 로그인 상태를 알고 유지하려면 브라우저 세션(쿠키)과 연동되는 별도 클라이언트가 필요합니다 — 이게 `@supabase/ssr` 패키지입니다.

**어떻게**: 세 개의 클라이언트/파일로 역할을 나눴습니다.
- `lib/supabase/browserClient.ts` — 클라이언트 컴포넌트(로그인 폼 등)에서 씀. `anon` 키 사용(공개돼도 안전 — RLS가 접근 범위를 제한).
- `lib/supabase/serverClient.ts` — 서버 컴포넌트/API 라우트에서 "지금 이 요청을 보낸 사람이 로그인했는지" 확인할 때 씀. Next.js의 쿠키 저장소를 읽어서 세션을 복원.
- `proxy.ts`(구 middleware.ts — 아래 설명) — 매 요청마다 세션 토큰을 갱신. **이게 없으면 액세스 토큰이 만료될 때마다 사용자가 이유 없이 로그아웃된 것처럼 보입니다** — Supabase 세션은 단기 토큰이라 서버 쪽에서 주기적으로 갱신해줘야 하는데, 서버 컴포넌트는 쿠키를 "쓸" 권한이 없어서(읽기만 가능) 이 refresh를 담당할 별도 진입점이 필요합니다.

**언제 실행되나**: `proxy.ts`는 정적 파일(이미지/CSS 등)을 제외한 모든 요청마다 실행되고, `serverClient.ts`는 서버 컴포넌트/API 라우트가 "누가 요청했는지" 알아야 할 때(예: 분석 요청에 user_id 붙이기, `/history` 페이지에서 로그인 여부 확인)마다 호출됩니다.

### 2) `proxy.ts` (구 `middleware.ts`)

빌드 중에 "middleware 파일 규칙은 deprecated, proxy로 바뀜"이라는 경고가 떠서 `node_modules/next/dist/docs/`에서 실제 문서를 확인하고 대응했습니다(AGENTS.md가 경고한 대로, 이 프로젝트의 Next.js 버전은 최신 문서를 직접 봐야 하는 케이스였습니다) — `middleware.ts` → `proxy.ts`, `export function middleware` → `export function proxy`로 이름이 바뀌었습니다. 기능은 동일합니다.

### 3) DB 스키마 v2 마이그레이션

| 이전 | 이후 |
|---|---|
| `images`(phash+판정+full_result 한 행) | `request_images`(이미지 정보) + `verification_evidence`(source별 판정) + `verification_results`(최종 판정) 분리 |
| `request_logs`(요청 메타 전부) | `verification_requests`(요청 메타, `user_id` 포함) |
| 없음 | `ai_provider_calls`(provider별 raw 로그 — 토큰/비용/지연시간) |
| 없음 | `users`(로그인 프로필) |

**`record_verification` RPC**: 위 5개 테이블을 트랜잭션 하나로 채우는 단일 함수. `lib/analysis/pipeline.ts`가 분석 끝날 때 이거 한 번만 호출합니다 — 이전엔 `insert_image_record` + `request_logs` insert 두 번이었는데, 이제 요청/이미지/provider호출×N/근거×N/최종결과까지 전부 원자적으로 기록됩니다(일부만 실패해서 데이터가 반쪽 나는 일이 없음).

**동일/유사 이미지 검색**(`find_similar_images`/`find_similar_by_embedding`)도 새 테이블 구조에 맞게 JOIN 기반으로 다시 짰습니다 — 응답 모양(TS 쪽 `SimilarImageMatch`)은 그대로라 `aggregator.ts`/`pipeline.ts`의 중복탐지 로직은 안 건드렸습니다.

**파일 구조 변경**: `lib/db/imageRecords.ts` + `lib/logging/analysisLogger.ts` → `lib/db/verification.ts` 하나로 통합. `extractRequestContext`(IP 추출)는 `lib/net/requestContext.ts`로 독립.

### 4) 로그인/회원가입 UI

- `app/login/page.tsx` — 이메일/비밀번호 + Google/카카오 버튼, 로그인↔회원가입 토글
- `app/auth/callback/route.ts` — 소셜 로그인/이메일 확인 후 돌아오는 콜백, 세션 교환
- `components/layout/AppHeader.tsx` — 로그인 상태에 따라 "로그인" 또는 "내 분석 이력"/"로그아웃" 표시

로그인 안 해도 기존처럼 전부 그대로 씁니다(분석/피드백 모두 비로그인 허용 유지) — 로그인은 "이력 보기" 같은 부가 기능을 여는 용도입니다.

### 5) `/history` — 내 분석 이력

로그인한 사용자의 `verification_requests`(+`verification_results`) 최근 50건을 보여줍니다. 비로그인 접근 시 `/login`으로 리다이렉트. RLS 정책(`auth.uid() = user_id`) 덕분에 서버 코드에서 별도로 "내 것만 필터링"하는 로직 없이도 안전합니다(그래도 명시적으로 `.eq("user_id", user.id)`도 같이 넣어서 이중 방어).

**참고**: 개별 분석 결과의 상세 화면(provider별 breakdown 등)으로 들어가는 링크는 이번엔 안 만들었습니다 — 그런 상세 페이지 자체가 아직 없어서(지금은 분석 직후 같은 페이지에서만 보임)입니다. 필요하시면 다음 라운드에 `/history/[requestId]` 같은 라우트를 만들 수 있습니다.

### 6) 피드백 — 로그인 시 user_id 자동 연결

`feedback` 테이블에 `user_id`(nullable) 추가, 로그인 상태면 자동으로 채워지고 비로그인이어도 그대로 제출 가능합니다(로그인을 피드백의 필수조건으로 만들지 않았습니다).
