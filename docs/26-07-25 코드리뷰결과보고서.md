## 핵심 답변 — pgvector 저장, 지금 잘 되고 있나요?

**아니요. `embedding` 컬럼은 완전히 미사용 상태이고, pgvector 기반 유사도 검색은 아직 코드 경로 자체가 존재하지 않습니다.**

- `supabase/schema.sql:26` — `images` 테이블에 `embedding vector(384)` 컬럼이 있고 `create extension if not exists vector;`(schema.sql:19)로 확장도 활성화돼 있습니다. 하지만 이건 자리만 만들어둔 것입니다(스키마 주석에도 "NULL"이라고 명시).
- `lib/db/imageRecords.ts:51-76`의 `insertImageRecord()`는 `phashHex`, `category`, `isAiGenerated`, `aiProbability`, `imagePath`, `mode`만 받고 **embedding 파라미터 자체가 없습니다.** `supabase/schema.sql:43-65`의 `insert_image_record()` RPC 함수도 embedding을 받는 인자가 없어서, TS/SQL 양쪽 다 이 컬럼에 값을 넣을 방법이 없습니다.
- 더 근본적으로, `ml/serve.py:94-96`의 `/infer` 엔드포인트는 `MODEL.predict_proba(emb...)`로 계산한 **`ai_probability` 숫자 하나만 반환**하고, 임베딩 벡터 자체(384차원)는 응답에 아예 포함하지 않습니다. `lib/analysis/dino.ts:52-53`도 `data.ai_probability`만 읽습니다. 즉 Next.js 쪽이 embedding을 저장하고 싶어도, 지금 프로토콜상 받을 방법이 없습니다.
- `lib/db/imageRecords.ts:26-44`의 `findSimilarImages()` → `supabase/schema.sql:72-98`의 `find_similar_images()`는 **pHash(bit(64)) Hamming distance만** 계산합니다(`bit_count(images.phash # p_phash_bits::bit(64))`). pgvector의 `<=>` (코사인 거리) 연산자나 HNSW 인덱스를 쓰는 쿼리는 어디에도 없습니다.

**정리**: 지금 "중복/유사 이미지 탐지"는 100% pHash Hamming distance만으로 동작하고 있고, 이건 재요청·재압축·색보정 수준의 근접 중복만 잡습니다(설계 의도상으로도 그렇습니다 — schema.sql 주석 참고). 사용자가 원하는 "pHash로 안 걸리면 pgvector로 의미적 유사 이미지를 찾아서 판정에 반영"하는 2단계는 **아직 스캐폴딩만 있고 실제로는 미착수**입니다. 이는 `docs/DEV_PROGRESS_MODULE_AB.md`의 진척표(6, 8번 항목)에도 이미 "미착수"로 정확히 기록돼 있어 여러분의 인식과도 일치합니다 — 이번 리뷰로 코드 레벨에서 그 사실을 재확인한 것입니다.

**다음 단계로 필요한 최소 변경**:
1. `ml/backbone.py`의 `embed_image()`가 이미 임베딩을 반환하므로, `ml/serve.py`의 `/infer` 응답에 `"embedding": emb.tolist()`를 추가.
2. `lib/analysis/dino.ts`에서 이 embedding을 받아 파이프라인까지 전달(`VisionResult`에 태우거나 별도 반환값으로).
3. `insert_image_record` RPC와 `insertImageRecord()`에 `p_embedding vector(384)` 파라미터 추가.
4. `find_similar_images`류의 RPC를 하나 더 만들어 `embedding <=> p_embedding` 코사인 거리로 kNN 검색(HNSW 인덱스 `create index ... using hnsw (embedding vector_cosine_ops)` 필요) 하고, `lib/db/imageRecords.ts`에 pHash에서 매치가 없을 때만 이 kNN을 호출하는 2단계 폴백 로직 추가.

### 1. LLM API 실패가 "판단 불확실"과 구분되지 않고 조용히 섞여 들어감

**파일**: `lib/vision/anthropic.ts:18,54,58`, `lib/vision/gemini.ts:16,42,46`, `lib/vision/openai.ts:38,66,72,76`, `lib/vision/normalize.ts:104-124`, `lib/analysis/aggregator.ts:59`

3개 LLM 모듈 전부, API 키 미설정·네트워크 예외·빈 응답 같은 **모든 실패 분기**에서 `normalizeModelResult(null, provider, modelName, { errorMessage })`를 호출하는데, `isMock` 옵션을 넘기지 않습니다. `normalizeModelResult`(`normalize.ts:104`)의 기본값은 `isMock = false`이므로, 실패한 호출도 `is_mock: false`로 반환됩니다.

그런데 `aggregator.ts:59`의 `visionResults.filter((r) => !r.is_mock)`는 **바로 이 `is_mock` 플래그만 보고** "실제 분석 결과"와 "무시해야 할 결과"를 나눕니다. 즉:

- **실패 시나리오**: `OPENAI_API_KEY`/`GEMINI_API_KEY`/`ANTHROPIC_API_KEY` 중 하나가 잘못 설정되거나 일시적으로 실패하면, 그 결과는 `score: 0.5, confidence: "low", is_ai_generated: null, is_mock: false`로 채워져서 aggregator에 **진짜 모델 투표처럼** 들어갑니다. 가중평균에 `score=0.5`가 섞이고, `hasVision`/`activeSignals`도 "정상적으로 분석했다"고 계산되어 vision multiplier가 적용됩니다. `final_result`에는 "3개 모델이 분석해서 불확실로 나왔다"는 결과만 남고, 실제로는 그중 하나(또는 전부)가 인증 실패였다는 사실이 **API 응답 어디에도 요약되지 않습니다** — `vision_results[i].error_message`를 개별로 뒤져야만 알 수 있습니다.
- 부분 실패(예: Gemini 키만 잘못됨)의 경우도 마찬가지로, 나머지 2개 모델이 낸 진짜 신호가 가짜 0.5표 하나에 의해 희석됩니다.

이건 유일하게 참인 배제 로직(`is_mock`)이 실패 경로에서 세팅되지 않아서 생기는 버그이므로, DINO(`dino.ts:78-93`, 여기는 `is_mock: true`를 정확히 설정함)와 비교하면 **3개 LLM 프로바이더의 실패 처리가 DINO보다 일관성이 떨어집니다.**

**권장 조치**: 세 프로바이더의 모든 에러 분기에서 `normalizeModelResult(null, provider, modelName, { errorMessage, isMock: true })`로 `isMock: true`를 명시. 또한 `final_result`나 응답 최상위에 "N개 프로바이더 실패"를 요약하는 필드를 추가하면 운영 중 조용한 열화를 감지하기 쉬워집니다.

### 2. `aggregator.ts`의 시각 근거 점수가 판정 방향과 무관하게 항상 AI쪽으로 가산됨

**파일**: `lib/analysis/aggregator.ts:76-79,105-106`

```ts
for (const item of result.evidence) {
  if (item.description) evidenceSummary.push(item.description);
  visualScore += VISUAL_EVIDENCE_POINTS[item.severity ?? "low"] ?? 1;   // 방향(real/AI) 구분 없음
}
...
finalScore += Math.min(visualScore, 25);   // 항상 양수로만 가산
```

`visualScore`는 evidence의 `severity`(low/medium/high)만 보고 점수를 매기는데, 이 evidence가 "AI 생성 근거"인지 "실제 촬영 근거"인지는 전혀 구분하지 않습니다. `finalScore`에는 항상 **양수로만** 더해집니다(최대 +25). 즉 어떤 모델이 "이 이미지는 확실히 실제 사진입니다"라고 근거를 강하게(`severity: high`) 제시해도, 그 확신은 finalScore를 AI 판정 쪽으로 밀어올립니다.

- **실패 시나리오**: DINO가 `probAi=0.004`(99.6% 확률로 real)로 판정하고 `confidence: high`(→ `severity: high`, `dino.ts:69`)인 evidence 1개를 반환하면, `visualScore += 5`가 그대로 `finalScore`에 더해집니다. real 판정에 대한 강한 확신이 오히려 최종 점수를 AI 쪽으로 밀어올리는 역설이 발생합니다.
- 이 항목은 계정 전환 전 진행 중이던 `/code-review lib` 리뷰(`docs/HANDOFF_2026-07-25.md` 참고)에서 이미 검증 전 후보로 나왔던 것으로, 이번에 직접 코드를 읽어 **확정(CONFIRMED)** 처리합니다.

**권장 조치**: evidence 루프에서 `result.is_ai_generated`(또는 `result.score >= 0.5`)에 따라 부호를 결정하거나, real 방향 근거는 별도로 감산하는 로직을 추가해야 합니다.

### 3. `toPercentageScore` — 정수 1(=1%)이 100%로 뒤집혀 표시됨

**파일**: `lib/utils/score.ts:1-4`, 호출부 `app/page.tsx:74`

```ts
export function toPercentageScore(score) {
  if (score === undefined || score === null || Number.isNaN(score)) return 0;
  if (score <= 1) return Math.round(score * 100);   // 0~1 소수라고 가정
  return Math.round(Math.min(score, 100));
}
```

이 함수는 "0~1 사이 소수" 입력과 "이미 0~100 정수" 입력을 `score <= 1`이라는 조건 하나로 구분합니다. 그런데 `app/page.tsx:74`는 `analysisResult.final_result.ai_probability`를 넘기는데, 이 값은 `aggregator.ts:108`에서 이미 `Math.max(0, Math.min(100, Math.round(finalScore)))`로 **0~100 정수**로 확정된 값입니다.

- **실패 시나리오**: `finalScore`가 정확히 `1`(=AI 확률 1%, 강하게 "실제 이미지"로 판정된 경우)이면 `toPercentageScore(1)`은 `1 <= 1` 조건에 걸려 `1 * 100 = 100`을 반환합니다. 헤드라인 점수가 **"AI 확률 1%"를 "AI 확률 100%"로 뒤집어 표시**하는 것으로, 이 함수가 담당하는 값 중 가장 심각한 방향의 오류입니다. (참고: `ProviderResultCard.tsx:50`에서 같은 함수를 개별 provider의 `score`(항상 0~1 소수)에 쓰는 건 정상 — 문제는 `app/page.tsx:74`의 호출부 하나뿐입니다.)

**권장 조치**: `final_result.ai_probability`는 이미 0~100 정수이므로 `toPercentageScore`를 거치지 말고 그대로 사용하거나, 함수 시그니처를 분리(`toPercentageScore` vs `clampPercentage`)해서 호출부 실수를 타입 레벨에서 막아야 합니다.

(현재 세션에서 `dinov3_vits16` 엔트리포인트가 실제로 dict를 반환하는지는 GPU 환경에서 직접 실행해야 확인 가능 — 코드 자체는 확실히 버그입니다.)

### 6. 세로(portrait) 사진의 EXIF 회전 후 리사이즈가 잘못된 축을 기준으로 계산됨

**파일**: `lib/image/preprocess.ts:19-34`

```ts
const image = sharp(inputBuffer, { failOn: "none" }).rotate(); // EXIF 자동 회전, 이후 스트립
const metadata = await image.metadata();   // ← 회전 "전" 원본 width/height
const width = metadata.width ?? 0;
const height = metadata.height ?? 0;
const longestSide = Math.max(width, height);
...
pipeline = pipeline.resize({
  width: longestSide === width ? longSide : undefined,
  height: longestSide === height ? longSide : undefined,
  ...
});
```

`sharp().metadata()`는 파이프라인에 `.rotate()`가 큐잉돼 있어도 **회전 적용 전** 원본 width/height를 반환합니다(EXIF orientation이 6/8이면 실제 출력은 가로/세로가 바뀝니다). 그런데 `resize()`는 `.rotate()` 뒤에 실행되므로 이미 회전된 이미지에 적용됩니다.

- **실패 시나리오**: 스마트폰이 흔히 저장하는 "가로로 저장되고 EXIF로 세로 회전 지정"된 사진(예: 원본 4032×3024, 회전 후 실제로는 3024×4032 세로) — `longestSide`가 원본 기준 `width=4032`로 판정되어 `resize({ width: 1024 })`가 적용됩니다. 하지만 회전된 실제 이미지는 세로가 긴 변(4032)이므로, `width=1024`만 지정하면 세로가 비율에 따라 `1024 × (4032/3024) ≈ 1365`까지 늘어나 **설정한 `IMAGE_LONG_SIDE` 상한(기본 1024)을 넘어섭니다.** 모든 LLM에 프로젝트 의도보다 큰 이미지가 들어가고(비용/속도 증가), 이미지 크기 정규화가 세로 사진에서 일관되게 깨집니다.
- 부수 효과: `lib/analysis/pipeline.ts:110`의 `AnalysisResult.input.width/height`도 같은 `originalMeta`(회전 전)를 그대로 쓰고 있어, 응답 JSON에 세로 사진의 가로/세로가 뒤바뀌어 노출됩니다.

**권장 조치**: `sharp`가 제공하는 `metadata.autoOrient.width/height`(회전 반영된 치수)를 기준으로 `longestSide`를 계산.

### 7. `metadata.ts` — PNG는 텍스트 청크 유무와 무관하게 항상 `png_metadata_found: true`

**파일**: `lib/analysis/metadata.ts:138-146`

```ts

if (Object.keys(pngInfo).length > 0) {
  if (isPng) pngMetadataFound = true;
  else if ([...].some((k) => k in pngInfo)) pngMetadataFound = true;  // isPng=false면 pngInfo는 항상 {}이라 도달 불가

```

`pngInfo`는 `isPng`가 false면 항상 `{}`이므로 `else if` 분기(`metadata.ts:141`)는 **죽은 코드**입니다. 그리고 청크가 하나도 없는 "깨끗한" PNG조차 `isPng`이기만 하면 `pngMetadataFound = true`가 됩니다.

- **실패 시나리오**: tEXt/iTXt 청크가 전혀 없는 순수 PNG를 업로드하면 `png_metadata_found: true`로 응답되어(`MetadataResultCard.tsx`에서 "메타데이터 발견" 배지로 노출) 실제로는 아무 근거가 없는데 있는 것처럼 보이고, `metadata.ts:194`의 `!exifFound && !pngMetadataFound` 조건이 항상 거짓이 되어 "메타데이터 부재는 흔한 상황" 안내 문구도 사라집니다.

**권장 조치**: `pngMetadataFound = Object.keys(pngInfo).length > 0`으로 단순화(첫 분기 자체가 `isPng`일 때만 `pngInfo`가 채워지므로 `isPng` 재확인 불필요).

### 8. Gemini 클라이언트만 타임아웃이 없음

**파일**: `lib/vision/gemini.ts:22`, 비교 대상 `lib/vision/anthropic.ts:26`, `lib/vision/openai.ts:48`

Anthropic/OpenAI는 `timeout: Number(process.env.REQUEST_TIMEOUT_SECONDS || 60) * 1000`을 SDK 클라이언트에 설정하는데, Gemini는 `new GoogleGenAI({ apiKey })`만 호출하고 `httpOptions.timeout`을 설정하지 않습니다(`@google/genai`가 이 옵션을 지원함에도).

- **실패 시나리오**: Gemini 쪽 네트워크가 멈추면 `lib/vision/errorMessage.ts`의 타임아웃 처리 분기를 아예 타지 않고 요청이 무한정 대기하며, `pipeline.ts:89`의 `Promise.all(providerCalls)`가 다른 2개 LLM과 DINO가 다 끝나도 Gemini 하나 때문에 전체 응답이 막힙니다.

**권장 조치**: `config.httpOptions.timeout`을 동일하게 설정.

### 9. `safeFetch.ts` 타임아웃이 응답 헤더까지만 커버, 본문 스트리밍은 무제한

**파일**: `lib/net/safeFetch.ts:93-110`(타임아웃 설정/해제), `136-148`(본문 읽기 루프)

`AbortController` 타이머가 `fetch()` 호출 전 시작되고 `fetch()`가 헤더를 받아 resolve되는 순간 `finally`에서 해제됩니다. 이후 실제 바이트를 받는 `reader.read()` 스트리밍 루프에는 시간 제한이 전혀 없고, `maxBytes` 크기 제한만 있습니다.

- **실패 시나리오**: 이미지 URL 분석 기능에 악의적/느린 서버가 연결은 즉시 받아주고(헤더 타임아웃 통과) 바이트를 아주 느린 속도로 흘리면, 크기 제한에는 안 걸리면서 시간 제한 없이 요청을 붙잡아둘 수 있습니다(slow-loris류의 소프트 DoS).

**권장 조치**: 스트리밍 루프 전체에도 동일한 `AbortSignal`(또는 전체 요청 기준 데드라인)을 적용.

### 10. 500 에러 응답에 원본 예외 메시지가 그대로 노출됨

**파일**: `app/api/analyze/image/route.ts:69,85`, `app/api/analyze/image-url/route.ts:56-61,77`

`ImageValidationError`(400)가 아닌 모든 예외는 `error.message`를 그대로 `detail` 필드에 담아 500으로 반환합니다.

- **실패 시나리오**: `sharp` 내부 오류(파일 경로 포함), Supabase/Postgres 오류 문자열, OpenAI/Gemini/Claude SDK 예외 메시지(계정/요청 관련 세부정보 포함 가능)가 인증되지 않은 클라이언트에게 그대로 노출될 수 있습니다.

**권장 조치**: 클라이언트에는 일반화된 메시지만 반환하고, 원본 메시지는 서버 로그(`logAnalysisEvent`는 이미 하고 있음)에만 남기기.

### 11. 압축된 iTXt 청크는 파싱하지 못해 AI 생성 흔적을 놓칠 수 있음

**파일**: `lib/analysis/metadata.ts:58-67`

iTXt 청크 파싱이 압축 플래그(compression flag)를 전혀 확인하지 않고 null 바이트 이후를 곧바로 UTF-8로 디코딩합니다. 압축 플래그가 1(zlib 압축)인 iTXt 청크는 이 방식으로 디코딩하면 의미 없는 바이너리 문자열이 나옵니다.

- **실패 시나리오**: 일부 AI 생성 도구가 `workflow`/`prompt` 필드를 압축된 iTXt로 저장하는 경우, `parameters`/`workflow` 키워드 매칭(`metadata.ts:152-174`)이 조용히 실패해 AI 생성 근거를 놓칩니다 — 이 프로젝트의 핵심 판정 기능과 직결되는 부분이라 우선순위를 medium으로 잡았습니다.

**권장 조치**: 압축 플래그 바이트를 확인해 압축된 경우 zlib inflate 후 디코딩(또는 최소한 압축 청크는 스킵하고 별도 evidence로 "압축된 메타데이터 존재"만 표시).

### 12. `ensureBucket()`이 `getBucket()` 에러를 무시해서, 권한 문제 시 매 요청마다 같은 실패를 반복

```ts
const { data: existing } = await supabase.storage.getBucket(BUCKET_NAME);  // error 필드 버림

```

`getBucket()`이 "존재하지 않음"이 아니라 권한/설정 오류로 실패해도 `data`만 보고 `existing`이 falsy면 매번 `createBucket()`을 다시 시도합니다. `bucketEnsured`는 성공 경로에서만 true가 되므로, service_role 키 권한이 잘못돼 있으면 **분석 요청마다** 이 왕복이 반복되고 매번 로컬 폴백으로 빠집니다(에러 자체는 잡혀서 분석은 안 죽지만, 매 요청 불필요한 네트워크 왕복 2회 추가). `docs/HANDOFF_2026-07-25.md`에 이미 후보로 있던 항목을 확인.

**권장 조치**: 실패도 캐싱(예: 짧은 TTL 또는 프로세스 수명 동안 1회만 재시도)하거나, 에러를 로그에 남겨 설정 문제를 조기에 발견할 수 있게.

### 13. `image_path`에 `supabase://...`와 로컬 상대경로 두 형식이 섞여 저장됨

**파일**: `lib/storage/imageStore.ts:51,64`, 저장처 `supabase/schema.sql:29`(`images.image_path`), `supabase/schema.sql:127`(`request_logs.image_path`)

### 15. URL 분석 모드에서 프리뷰 이미지가 실제 분석된 바이트와 다를 수 있음

**파일**: `app/page.tsx:90`, `components/results/ImageCanvasWithBoxes.tsx:28-33`

**권장 조치**: 분석 응답에 `finalUrl`(또는 서버에 저장된 이미지의 signed URL)을 포함해 클라이언트가 그걸로 프리뷰를 렌더링.

## 확인했지만 문제 없음(참고용 — 잘 짜인 부분)

리뷰 중 "버그일 수 있겠다" 싶어 깊게 봤지만 실제로는 견고하게 처리된 부분들입니다:

- **SSRF 방어** (`lib/net/safeFetch.ts`) — `image-url` 라우트의 URL 분석 경로는 `localhost`, `169.254.169.254`(클라우드 메타데이터 엔드포인트), 모든 RFC1918/링크로컬/루프백 대역, IPv6 동급 대역을 차단하고, 리다이렉트마다 재검증합니다. 잘 만들어져 있습니다. (DNS 재바인딩 TOCTOU 여지는 낮은 심각도로 위 15번 근처에 남겨둘 만하지만, 이번 10개 우선순위 항목에는 넣지 않았습니다.)
- **XSS** — `components/results/*`, `app/page.tsx`에 `dangerouslySetInnerHTML` 없음, 모델이 반환한 텍스트도 전부 JSX 텍스트 보간(자동 이스케이프)으로 렌더링됩니다.
- **pHash 알고리즘 자체** (`lib/analysis/phash.ts`) — DCT 구현, 중앙값 임계값, hex 패킹까지 정확합니다.
- **ml 파이프라인의 라벨/인덱스 정합성** — `extract_embeddings.py`/`train_linear_probe.py`의 embeddings/labels/categories 배열이 항상 같은 루프에서 함께 채워지고, 실패한 이미지는 네 배열 모두에 동시에 반영되지 않아 인덱스가 어긋나지 않습니다.
- **serve.py 동시성** — `ThreadingHTTPServer` 아래에서 `MODEL`은 읽기 전용으로만 쓰이고, 요청마다 `tempfile.mkstemp()`로 고유 임시파일을 쓰므로 동시 요청 간 충돌이 없습니다.

## 열린 질문에 대한 의견 — 익스텐션 별도 repo?

지금 단계(초기, 팀 1개, API 계약이 계속 바뀌는 중)에서는 **같은 repo 안에 `extension/` 폴더로 두는 걸 권합니다.** 이유:

- 웹서비스 API 응답 스키마(`types/analysis.ts`)가 아직 유동적입니다(이번 리뷰에서도 `evidence`/`score` 방향성 버그가 나올 정도). API가 바뀔 때마다 별도 repo면 두 저장소를 오가며 버전을 맞춰야 하는데, 지금은 그 오버헤드가 이득보다 큽니다.
- Chrome 확장은 결국 이 웹서비스의 API를 호출하는 얇은 클라이언트라, 지금은 강하게 결합돼 있습니다.

**분리를 고려할 시점**: API 계약이 안정화되고, 확장 프로그램만의 릴리스 주기(예: Chrome 웹스토어 심사 대기)가 웹서비스 배포를 막기 시작하거나, 확장 프로그램을 별도 팀/일정으로 운영하게 될 때. 그전까지는 모노레포 쪽이 되돌리기도 쉽습니다(나중에 폴더 하나를 새 repo로 떼어내는 게, 반대로 두 repo를 하나로 합치는 것보다 훨씬 간단합니다).
