## 1) 마케팅 랜딩페이지 시안과 UI 정렬

### 확인 방법에 대한 정직한 답변
저는 브라우저를 직접 띄울 수 없어서, `index.html`을 실제로 "구동"(클릭·스크롤 인터랙션 확인)해보지는 못했습니다. 대신 `index.html`, `css/style.css`, `js/main.js`, `result.html`, `js/result.js`를 **전체 다 읽어서** 정적으로 분석했습니다 — 특히 `main.js`는 이번에 처음 끝까지 읽었는데, 스크롤에 연동된 아치형 카드 회전 + 카드 하나가 날아가서 결과 패널에 안착하는 애니메이션, HIVE 스타일 데모 패널, 유스케이스 캐러셀 등 복잡한 스크롤재킹 연출이 전부였습니다.

### 적용 범위 결정
지난 라운드에서 "다크테마로 전면 교체"를 선택하셨을 때 이미 실제 앱(`app/page.tsx` 등)에 다크테마 + 톤 기반(빨강/초록) 색상 체계를 입혀뒀습니다. 이번엔 마케팅 랜딩페이지의 **복잡한 스크롤 애니메이션 자체는 포팅하지 않았습니다** — 실제 서비스 페이지(업로드→분석→결과)와 마케팅 데모 애니메이션은 목적이 달라서(전자는 반복 사용하는 도구, 후자는 1회성 임팩트용 데모), 이번 요청의 핵심인 "**자세히 보기 버튼**"과 **UI 톤 일치**에 집중했습니다.

### 실제로 반영한 것
`result.html`의 핵심 UX 패턴 — **요약이 먼저 뜨고, "자세한 분석 보기" 버튼을 눌러야 상세 내역(모델별 breakdown)이 펼쳐지는 구조** — 를 `app/page.tsx`에 그대로 포팅했습니다:
- `showDetail` 상태 추가 (기본값 `false`)
- 종합점수/핵심결과/근거/해석 카드 아래에 "자세한 분석 보기" ↔ "분석 접기" 토글 버튼 추가 (`result.html`의 `#detailBtn`과 동일한 동작 — 클릭 시 펼쳐지고 텍스트가 바뀌고 그 위치로 스크롤)
- 토글이 열리면 그 아래에 비전 모델별 카드 + 의심 부위 캔버스 + 메타데이터 카드가 나타남 (기존엔 전부 상시 노출이었음)

## 2) 피드백 기능

`result.html`의 `.feedback` 섹션(제목 + textarea + 제출 버튼 + 완료 토스트)을 그대로 UI에 반영하되, **실제로 저장되도록** 구현했습니다(원본 시안은 `sessionStorage`에도 안 남기는 프로토타입이었음):

| 파일 | 역할 |
|---|---|
| `supabase/schema.sql` | `feedback` 테이블 신규 (id, request_id, message, ip, user_agent, created_at) |
| `app/api/feedback/route.ts` | POST — rate limit 적용, 메시지 길이 제한(2000자), Supabase insert |
| `components/results/FeedbackForm.tsx` | textarea + 제출 버튼 + 성공/실패 메시지, `app/page.tsx` 결과 화면 맨 아래 배치 |

로그인이 없으므로 익명 제출이고, `request_id`는 어떤 분석 결과에 대한 피드백인지 참고용으로만 남습니다(FK 아님 — `images`/`request_logs`가 나중에 지워져도 피드백은 남아야 해서).

## 3) 로그인/회원가입 — 보류 확인

말씀하신 대로 **로그인 없이 사용 가능한 상태를 유지**했습니다. 코드베이스 전체(`app/`, `components/`)를 검색해서 sign-in/sign-up 관련 UI가 전혀 없는 것도 확인했습니다. 새 기능(피드백, 자세히 보기)도 전부 로그인 불필요하게 만들었습니다.

요청하신 4가지 항목 + 추가로 발견한 것 하나, 실제로 코드를 grep하고 대조해서 확인했습니다.

| 항목 | 상태 | 근거 |
|---|---|---|
| 파일 확장자 검증 | ✅ 기존에 구현됨 | `app/api/analyze/image/route.ts` — 업로드 파일명 확장자 1차 필터 |
| 정상 이미지인지 검증 | ✅ 기존에 구현됨 | `lib/analysis/pipeline.ts`의 `ALLOWED_FORMATS` — sharp가 실제로 디코딩한 바이트 기준(파일명·Content-Type은 신뢰 안 함) |
| 코드 업로드(위장 이미지) | ✅ 구조적으로 방어됨 | ① SVG(스크립트 삽입 가능한 유일한 "이미지" 포맷) 자체가 `ALLOWED_FORMATS`에서 제외됨 ② 업로드 원본 바이트는 저장/서빙되지 않고, sharp가 픽셀 단위로 디코딩→JPEG 재인코딩한 결과만 저장됨(`preprocessImage`) — 폴리글랏 파일이어도 재인코딩 과정에서 이미지가 아닌 바이트는 전부 사라짐 |
| URL 업로드 시 SQL 인젝션 | ✅ 구조적으로 해당 없음 | `lib/db/`, `app/api/` 전체 grep — 문자열 조합으로 SQL 만드는 코드 없음, 전부 Supabase RPC/파라미터화된 호출만 사용 |
| SSRF | ✅ 기존에 구현됨 | `lib/net/safeFetch.ts` — 사설 IP/loopback 차단, DNS 재검증, redirect마다 재검증, Content-Type 화이트리스트 |
| SSTI | ✅ 구조적으로 해당 없음 | `eval`/`new Function`/템플릿 엔진 전체 grep — 사용처 없음. React JSX는 빌드 타임에 컴파일되지 문자열을 런타임에 해석하지 않아 SSTI 벡터 자체가 없음 |
| **XSS (신규 발견 → 수정 완료)** | 🔧 **취약점 발견, 수정함** | 아래 참고 |

### 신규 발견: Chrome 확장의 XSS 취약점

`extensions/chrome/sidepanel.js`가 `innerHTML`로 DOM을 조립하는데(React처럼 자동 이스케이프가 안 됨), **EXIF Make/Model/LensModel 값**을 이스케이프 없이 그대로 삽입하고 있었습니다. 이 값들은 업로드하는 사람이 exiftool 같은 도구로 얼마든지 임의 문자열(`<img src=x onerror=...>` 등)로 조작해서 넣을 수 있는 필드라, 실제 공격 벡터였습니다. Provider 에러 메시지(외부 API 응답을 일부 포함)도 같은 문제가 있었습니다.

**수정**: `escapeHtml()` 헬퍼를 추가해서 `innerHTML`에 들어가는 모든 외부 유래 값(EXIF 필드, provider 에러 메시지)에 적용했습니다. 웹앱(React)은 원래부터 안전했습니다 — `dangerouslySetInnerHTML` 사용처가 전체 코드베이스에 전혀 없는 것도 확인했습니다.
